# Gap versus Gaea

Every number here is regenerated by `python tools/gap-report.py` from the committed
catalogue and registry — none of it is quoted from memory. Evidence for the *reasons* is
cited by file.

## 1. Coverage

| Measure | Value |
| --- | --- |
| Catalogue nodes (`Nodes.json`, Gaea 2.3.1) | **182** |
| Registry entries carrying a kernel | 56 |
| …of which are actual catalogue nodes | **46 (25.3%)** |
| Catalogue nodes with **no** implementation | **136 (74.7%)** |
| Catalogue parameters declared | 1192 |

The 10 registry entries that are not catalogue nodes are this build's own plumbing:
`Group`, `Output`, `Blend`, `Invert`, and the six `*Select` nodes.

## 2. Fidelity of what IS implemented

The registry labels every node honestly, and that label is the interesting number:
"implemented" does not mean "matches Gaea".

| Label | Count | Meaning |
| --- | --- | --- |
| `approx` | 25 | same family of algorithm, parameters mapped onto it |
| `model` | 18 | Gaea's method is unavailable; a standard published model stands in |
| `exact` | 2 | only `Constant` and `Output` — nodes with no algorithm to speak of |
| `stub` | 1 | `File` (an I/O placeholder) |

**Only 2 of 182 nodes are claimed exact, and neither is a terrain algorithm.**

## 3. Why there is no full replication

This is not a matter of effort remaining. Three layers of the dependency stack exist, and
only one of them was recoverable.

### Layer 1 — managed C#: recovered, partially

`evidence/decompiled/` holds **76 decompiled `.cs` files** recovered with
`System.Reflection.Metadata` over the shipped PE images. This is where node *declarations*
live: names, parameter attributes, enum members, port wiring. It is the source of the
catalogue and of `docs/node-specs-from-il.json`.

Two defects limit it:

- **Eazfuscator.NET** replaced internal/private names with private-use-area characters and
  moved every numeric and string literal into an encrypted constant pool. The string pool
  was restored (1020 entries); **the integer pool was not**, so numeric defaults and ranges
  come from `[Parameter]` attributes rather than from the code.
- The decompilation is **partial**: 2 MB of `Gaea.Nodes.dll`. The inventory states plainly
  that *"node call sites that are not in it remain unmapped."*

### Layer 2 — C++/CLI wrappers: names only

`Gaea.CE.dll`, `Gaea.CS.dll`, `Gaea.CW.dll`, `Gaea.TS.dll` are the wrapper layer between
the C# nodes and the native kernels. Their export/import linkage was read.

Critically, they **contain no textual reference to a backend library** — the backend is
selected at runtime through function pointers resolved in `Gaea.Dv.dll` / `Gaea.Engine.dll`.
So even the call graph does not statically say which native kernel a given node reaches.

### Layer 3 — the native SYCL kernels: NOT recovered

The algorithms themselves live in `Gaea.Native.dll`, `Gaea.oneAPI.dll`,
`Gaea.AdaptiveCpp.dll`, `Gaea.AdaptiveCpp.HIP.dll`.

From `docs/kernels-inventory.json` → `limitations`, verbatim:

> Gaea.Native/oneAPI/AdaptiveCpp **ship no PDB and were not disassembled**: only symbol
> names, signatures, string tables and import linkage were read. **Bodies, constants,
> branch structure** […] Parameter struct ABIs: metadata order is recorded, but the native
> C++ struct layout was not read, so byte offsets are not asserted.

`evidence/` contains **zero** `.cpp`, `.h`, `.hpp` or `.cu` files. What was recovered is
the kernel **interface** — 15 signatures — not the mathematics:

    ParallelErosion, Thermal2, ThermalShaper, Flow, ColorTransport, MedianFilter,
    Cellular3D, MeshRasterizer, NativeLighting, Debris, Snow, Water, ClassicErosion,
    Resampling, StampInstancer

**15 known kernel surfaces against 136 unimplemented nodes.** For most missing nodes not
even the kernel signature is known.

### The consequence, stated plainly

Every terrain algorithm in this build is a **published algorithm fitted to Gaea's parameter
names**, not a transcription of Gaea's code. That is why `approx` and `model` exist as
labels and why they dominate the table in section 2. It is also why `Erosion2` — even now
that it uses a Laplacian pyramid with coarse-to-fine erosion, matching Gaea's structure —
is still `model`: the *structure* follows Gaea, the *per-level droplet arithmetic* is
Hansson's published formulation, because the SYCL body was never read.

## 4. Discrete behavioural gaps that are known and unfixed

| Area | Gap |
| --- | --- |
| Erosion | pyramid structure matches; per-level arithmetic is a published model |
| 136 nodes | absent entirely |
| Untouched parameters | a node that ignores a parameter silently uses the default, which is a behaviour difference and not cosmetic |
| Integer constants | Gaea's numeric defaults/ranges not restored from IL; only `[Parameter]` metadata |
| Native backends | no disassembly, no PDB, so no body-level ground truth exists for any kernel |
| Legacy wrapper variants | `ErosionWrapper` (C++/CLI) vs SYCL `ParallelErosion` not distinguishable statically |

## 5. What full replication would actually require

In increasing order of cost, and none of it is "more polishing":

1. **Disassemble the native kernels** (Ghidra/IDA on `Gaea.oneAPI.dll` etc.). The user
   explicitly chose *not* to install Ghidra earlier, so this path is currently closed by
   decision, not by capability. It is also the only path to true algorithmic parity.
2. **Or call Gaea's own DLLs** at runtime — which converts the project from a
   reimplementation into a wrapper, and was rejected in the same decision.
3. **Implement the remaining 136 nodes from their published literature** where an
   equivalent algorithm exists. This improves *breadth* and *plausibility*, never *parity*,
   and cannot be verified against Gaea for the same reason as above.

Items 1 and 2 are the only routes to "完整复刻" in the strong sense. Both need an explicit
decision because both change what this project *is*.
